# DB-TestGen R2 PostgreSQL benchmark

Copy the `backend/` directory into the repository root. No existing files are replaced.

## 1. Generate PostgreSQL test cases (no SQL executed)

```powershell
cd "C:\Users\keyag\AI-Assisted-Test-Case-Generator\backend"
python evaluate_dbms_r2_postgres.py
```

This creates `benchmark_results/postgres_review_<timestamp>.json` and prints its SHA256.
It uses the existing 12-scenario fixture, maps SQLite-specific *expert oracle error substrings* to PostgreSQL error substrings, and keeps the independent assertions unchanged. The fixture is not modified.

## 2. Review and use a disposable database

Review **every** `setup_sql`, `test_sql`, and `verification_assertions[].query` in the generated JSON. Do not approve SQL containing multiple statements, schema-qualified references outside the sandbox, or commands beyond simple CREATE TABLE, INSERT, UPDATE, DELETE and SELECT. This review is not an automated safety guarantee. PostgreSQL supports functions and other SQL constructs that can have side effects. The restricted role and transaction rollback do not make untrusted SQL safe. Use a disposable isolated container, not the long-lived development database; no production credentials or data.

After review, calculate the hash of the exact file you approved:

```powershell
Get-FileHash .\benchmark_results\postgres_review_<timestamp>.json -Algorithm SHA256
```

Point `DBTESTGEN_POSTGRES_URL` at the disposable PostgreSQL instance, using the restricted runner credentials and `dbtestgen_sandbox` schema already configured there.

## 3. Evaluate reviewed SQL

```powershell
python evaluate_dbms_r2_postgres.py --reviewed-file .\benchmark_results\postgres_review_<timestamp>.json --approved-sha256 <paste-hash>
```

The script refuses a changed review file, executes each test using the existing PostgreSQL validator, independently re-executes it using the benchmark's own assertions, and saves a timestamped JSON report.

## Caveats

- The PostgreSQL error mappings are generic substrings, not proof of semantic equivalence for every constraint. Review the benchmark and resulting errors.
- Existing SQLite and PostgreSQL results are not directly comparable as a controlled model study without matching evaluation conditions.
- The benchmark uses the *generated setup SQL*, so the independent oracle verifies the post-operation state against expert assertions, but cannot independently guarantee that generated preconditions match the requirement. Inspect preconditions when reviewing.
- Running PostgreSQL SQL generated by a model carries risk. A hash and manual review are gates, not a sandbox. Use a truly disposable environment.
